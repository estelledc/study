## 是什么

c12 是 unjs 的 **智能配置加载器**：同一份名字下，它会读主配置文件、rc、可选的 `package.json` 字段，再用 `defu` 叠成一层。日常类比：不是只找一张名片，而是把桌上、抽屉和信封里的纸条按优先级贴成一张表。

```js
import { loadConfig } from 'c12'

const { config, configFile, layers } = await loadConfig({ name: 'myapp' })
```

固定 `3.3.4` 默认找 `myapp.config.*`（以及 `.config/` 下的同名变体）和 `.myapprc`。`dotenv` 与 `packageJson` 默认关着。

## 为什么重要

不看固定 `loadConfig`，容易把“Nuxt 能读的所有层”写成 c12 的出厂行为：

- 为什么只调 `loadConfig({})` 不会读 `.env`——`dotenv` 默认 `undefined`，要显式打开
- 为什么 home 目录的 rc 不一定进来——只有 `globalRc` 才会并入 workspace / user rc
- 为什么主文件导出数组时，rc 和 defaults 都消失——数组走旁路，不 merge、不 extend
- 为什么 `extends: 'gh:org/template'` 会在磁盘留下克隆——`giget` 前缀会下载到 `.c12` / 缓存目录

一句话：它是 **多源合并器**。若你只要“找到第一份文件就停”，对照 [[cosmiconfig]]。

## 核心要点

固定 3.3.4 的主链可以拆成六步：

1. **补默认名**：`cwd` 是 `process.cwd()`；`name` 默认 `"config"`；主文件名是 `config` 或 `${name}.config`；rc 是 `.${name}rc`。`envName` 默认 `process.env.NODE_ENV`。
2. **可选 dotenv**：`setupDotenv` 默认读 `.env`、插值、跳过 `_` 前缀键；进程里已有的键不被覆盖，除非该键先前由 c12 自己写入。
3. **解析主文件**：先当本地路径，再试 `.config/` 去 `.config` 后缀、再试 `.config/` 原名。`.jsonc` / `.json5` / `.yaml` / `.toml` 走 confbox；其余交给 jiti（`interopDefault: true`）。导出若是函数，会用 `options.context` 调用。
4. **收 rc 与 package.json**：cwd 的 rc 总会读（除非 `rcFile: false`）。`globalRc` 才追加 workspace / home。`packageJson` 默认真关。
5. **defu 合并**：overrides → main → rc → packageJson → defaultConfig，再叠 `defaults`。源码注释写明下一 major 可能改顺序。
6. **extends**：默认键名 `extends`。字符串、数组或 `{ source, options }` 都接受。`gh:` / `github:` / `gitlab:` / `bitbucket:` / `http(s):` 走 giget；npm 包名会 `resolveModulePath`。

`$production` / `$env.production` 这类环境块叠在**该层**之上。`watchConfig` 包一层 chokidar，但 home/workspace rc 还不在 watchingFiles 里。

## 实践示例

### 案例 1：只合并主文件和 cwd rc

```js
const { config, layers } = await loadConfig({ name: 'myapp' })
```

会尝试 `myapp.config.*` 与 `.myapprc`。没有 dotenv，也不会读 `package.json` 的 `myapp` 字段。

### 案例 2：打开环境文件和 package.json

```js
const { config } = await loadConfig({
  name: 'myapp',
  dotenv: { fileName: ['.env', '.env.local'] },
  packageJson: true,
})
```

`.env.local` 写在后面，后写的 dotenv 键可以覆盖先写的；真正的进程环境仍优先，除非该键是 c12 自己填进去的。

### 案例 3：extends 到本地目录

```js
export default {
  extends: ['./base.config'],
  port: 4000,
}
```

`extendConfig` 会先删掉 `extends` 键，再递归加载基底；当前文件经 defu 压过图层。远程 `gh:` 源会先克隆再当目录解析。

## 踩过的坑

1. **以为默认会读 `.env`**：必须 `dotenv: true` 或传选项对象。
2. **把 README 的“Global RC”当成总会发生**：home / workspace rc 依赖 `globalRc`。
3. **主文件 `export default []` 还指望和 rc 合并**：数组直接成为 `config`，extend 也不会跑。
4. **把 npm latest 4.0.0-beta.5 的依赖图套到 3.3.4**：稳定线仍带 jiti / dotenv / giget / chokidar；beta 依赖面更窄，不能混读。
5. **克隆目录已存在就当缓存命中**：已存在且未要求 `install` 时，源码会先 `rm` 再 `downloadTemplate`。

## 适用 vs 不适用场景

**适用**：

- 工具或元框架要一份可 extends 的分层配置，而不是单文件命中
- 需要 jiti 直接读 TS，或 confbox 读 jsonc / toml / yaml
- 调用方能接受 dotenv 写进 `process.env` 的副作用

**不适用**：

- 只要约定 rc 搜索、由调用方自己合并——那是 [[cosmiconfig]]
- 不能让配置加载器改进程环境
- 准备跟 4.0 beta 走，却仍按 3.3.4 推理
- 要把未测的合并耗时或克隆网络表现写成结论

## 学到什么

1. **默认层比 README 列表更瘦**——dotenv、package.json、global rc 都是开关。
2. **defu 的第一参赢**——overrides 压 main，main 压 rc；数组主配置则整段替换。
3. **extends 是递归图层，不是字符串拼接**——远程前缀会落地成目录。
4. **监视 ≠ 读过的每一层**——`watchConfig` 还没把 home/workspace rc 放进 watchingFiles。

## 应用型自测

1. `await loadConfig({ name: 'myapp' })` 会不会自动读 `.env`？
2. 主配置 `export default [1, 2]` 时，cwd 的 `.myapprc` 还会并进去吗？
3. 不设 `globalRc` 时，用户家目录的 rc 会进入 `rawConfigs.rc` 吗？

检查点：

1. 不会。`dotenv` 默认关闭。
2. 不会。主配置是数组时直接采用，跳过 merge / extend。
3. 不会。只有 `globalRc` 才会读 workspace 与 user rc。
